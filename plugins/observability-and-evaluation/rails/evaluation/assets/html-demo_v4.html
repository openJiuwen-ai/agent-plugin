    Failure taxonomy
    
      
    
      
    
    
    
    
    
      
    Failure detection methods
    
      
    
              
    Zero-shot · without supplied failure knowledge
    
              
    One judge call reviews the trajectory without a failure taxonomy in the prompt. Findings use free-text failure labels, providing a baseline for comparison.
    
              
    Taxonomy-guided · with expert failure knowledge
    
              
    One specialist judge call per top-level taxonomy category, run concurrently: 7 for RAMS or 3 for MAST. Findings use taxonomy codes and are merged by trajectory step.
    
            
    
    
    
          
    
            
    Understanding the trajectory data model
    
            
    A trajectory records a workflow’s execution: its overall context, the agents involved, and their model calls, tool interactions, and outputs.
    
            
    The Trace Data Model provides a consistent structure for recording agent activity across different workflow architectures, so trajectories can be interpreted and evaluated in the same way. Each execution produces a standardized agentic_trajectory.json conforming to Trace Data Model v2.0.0, which provides direct input to the failure evaluation pipeline.
    
            
    
              Workflow level
              
    
                
    trace_metadata
    
                
    Describes the whole run: schema version, framework, scenario, architecture, timing, token usage, execution order, and overall status.
    
                
    agents
    
                
    Contains the recorded agent executions. An agent can appear more than once when it is invoked repeatedly or a workflow loops.
    
              
    
            
    
            
    
              Agent level
              
    
                
    agent_metadata
    
                
    Identifies the agent and records its system prompt, timing, model and tool call counts, token usage, and status.
    
                
    task / query
    
                
    The agent’s input: task.user_prompt in sequential, shared-context, and looping workflows, or query.recent_query in hierarchical invocations.
    
                
    llm_request_<i>
    
                
    A model call, including the model, timing, token usage, and how the call finished. Numbered blocks repeat as calls occur.
    
                
    tool_execution_activity_<i>
    
                
    A tool interaction, grouping the request, result, timing, and any nested reflection.
    
                
    tool_llm_request / tool_llm_request_<i>
    
                
    A model call that reflects on tool results. It can be nested inside a tool activity or recorded at agent level with links to the activities it reflects on.
    
                
    result
    
                
    The agent’s output, its step ID, and output token count.
    
                
    OTel_traces
    
                
    The captured OpenTelemetry spans containing lower-level execution details.
    
              
    
              
    Model-call, tool-activity, and reflection blocks appear when those interactions are recorded.
    
            
    
            
    
              Tool activity
              
    
                
    tool_calling
    
                
    Which tool was requested, its arguments, call ID, and execution status.
    
                
    tool_call_result
    
                
    The returned output, parsed result, errors, and timing. The call ID links the result to its request.
    
                
    tool_llm_request (optional)
    
                
    For a single tool interaction followed by model reflection, the reflection is nested here. Reflection on a batch or chain of tool activities is recorded at agent level using reflects_on_activities.
    
              
    
            
    
            
    
              Execution order and step IDs
              
    step_id identifies a recorded step. Top-level step IDs advance across the workflow, continuing across agents and loop attempts. They are strings, not decimal numbers.
    
              
    Dotted IDs identify parts within a tool activity: for activity 3, 3.1 is the tool request, 3.2 is its result, and 3.3 is the nested reflection when present.
    
              
    The number in a block name such as llm_request_1 identifies a repeated block; its step_id places it in the workflow’s execution order.
    
            
    
            
    
              Agentic workflow patterns
              
    These workflow patterns describe how agents collaborate and how work progresses. Each produces a trajectory described by the same data model.
    
              
    
                
    PatternHow agents work together
    
                
                  
    SequentialThe output of one agent seeds the next agent’s input.
    
                  
    Shared contextAgents work with one shared conversation history, including earlier agents’ turns and tool interactions.
    
                  
    LoopingThe workflow repeats through quality assurance (QA) attempts. The trajectory retains the repeated executions.
    
                  
    HierarchicalA supervisor delegates tasks to a team and coordinates agent invocations.
    
                    
              
    
              
    Workflows with a shared session are recorded with system_architecture set to shared_context. Older exports may use sequential for the same pattern.
    
              
    How these workflows appear in the trajectory
    
              
    
                
    Sequential, shared session, and looping workflows
    
                
    Each entry in agents contains an agent trace directly. Looping workflows keep the repeated attempts as separate entries.
    
                
    Hierarchical workflows
    
                
    team_configuration describes the team and its invocations; workflow_summary describes the orchestrator’s task, execution order, and aggregate usage. Agent invocations in agents are wrapped with sequence, agent_name, invocation_info, and an execution containing the agent trace.
                  
    Note — Hierarchical initialization: Sequence 0 contains orchestrator setup and team composition. Its execution has an initialization structure rather than an agent trace.
    
                
    
              
    
              
    This guide describes schema 2.0.0. Earlier trajectories without a schema_version use some different field names.
